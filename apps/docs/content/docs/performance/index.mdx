## Fairness Guarantees

Fairness is validated mechanically, not assumed. `pnpm bench:validate` boots every server and
asserts they agree before any timing happens; the runner also runs it as a pre-flight and
aborts on mismatch.

- **Byte-identical bodies** — for the 8 identical-work scenarios, all servers return the same
  response bytes, built from one shared payload module (only the random POST `id` and timestamps
  are normalized).
- **Identical middleware headers** — the 5-layer scenario sets the same five headers in every
  framework; a missing or differing header fails validation.
- **Identical runtime config** — same Node flags, `NODE_ENV=production`, port, and payloads.
- **Publishable = multi-run** — only the `standard` (3 runs) and `full` (5 runs) profiles may
  back published numbers; each reports mean ± stddev and CV. Single-run `quick` reports are
  stamped **NOT publishable**.

<Callout type="info" title="Two scenarios are intentionally not like-for-like">
  The **middleware-stack** and **error-handling** scenarios use each framework's idiomatic
  mechanism (Koa/Express/Hono/NextRush middleware chains, Fastify `onRequest` hooks, raw-node a
  manual function chain; dedicated error handlers vs a local catch). They measure per-framework
  5-layer and error-path cost — not one shared mechanism — and are labeled as such.
</Callout>

## Scenarios

<Tabs items={['Hello World', 'Route Parameters', 'POST JSON', 'Middleware Stack']}>
  <Tab value="Hello World">
    Baseline — a JSON response with no routing or body parsing.

    ```ts
    router.get('/', (ctx) => ctx.json({ message: 'Hello World' }));
    ```

  </Tab>

  <Tab value="Route Parameters">
    Dynamic route — measures router parameter extraction.

    ```ts
    router.get('/users/:id', (ctx) =>
      ctx.json({ id: ctx.params.id, name: `User ${ctx.params.id}`, email: `user${ctx.params.id}@example.com` })
    );
    ```

  </Tab>

  <Tab value="POST JSON">
    POST with a JSON body — body-parser overhead. The handler echoes the parsed body inside a
    wrapper (matching every server's response).

    ```ts
    import { json } from '@nextrush/body-parser';

    router.post('/users', json(), (ctx) =>
      ctx.json({ success: true, user: { id: /* random */ 0, ...ctx.body, createdAt: new Date().toISOString() } })
    );
    ```

  </Tab>

  <Tab value="Middleware Stack">
    Five middleware layers, each setting one response header (`X-Request-Id`, `X-Timestamp`,
    `X-Framework`, `X-Version`, `X-Processed`). This measures 5-layer dispatch cost — each
    framework implements the layers with its own idiomatic mechanism, so this is per-framework
    cost, not a like-for-like middleware race (see the note above on non-like-for-like scenarios).

    ```ts
    // Per-route middleware — modern ctx.next() (the (ctx, next) signature also works).
    const layer = (name, value) => (ctx) => { ctx.set(name, value); return ctx.next(); };
    router.get('/middleware', layer('X-Request-Id', '12345'), /* …4 more… */ (ctx) =>
      ctx.json({ middleware: true, layers: 5 })
    );
    ```
  </Tab>
</Tabs>

The full list — hello-world, json, route-params, query-string, post-json, deep-route,
middleware-stack, error-handling, large-json, empty-response — is defined in
`apps/benchmark/config/scenarios.js`.

## Design Trade-offs: Fastify vs NextRush

Fastify typically edges ahead on raw Node.js throughput. Here is what drives the gap:

<DocTableWrap>

| Area               | Fastify                            | NextRush                    |
| ------------------ | ---------------------------------- | --------------------------- |
| JSON serialization | AOT with `fast-json-stringify`     | Native `JSON.stringify`     |
| Router             | `find-my-way` (radix tree, mature) | Custom segment trie (newer) |
| Schema validation  | Compiled JSON Schema               | Standard Schema via `@nextrush/validation` (Zod, Valibot, ArkType) |
| HTTP parsing       | Custom optimized                   | Standard Node.js parser     |

</DocTableWrap>

<Callout type="info" title="Trade-off">
  Fastify tunes heavily for single-platform Node.js throughput. NextRush prioritizes **zero
  dependencies**, **full TypeScript**, and **multi-runtime support**. If single-platform HTTP
  throughput is your only concern, Fastify is an excellent choice. If you need portability and a
  lean, dependency-free core, NextRush optimizes for different terms.
</Callout>

## Run Your Own Benchmarks

```bash
cd apps/benchmark
pnpm install

# 1. Confirm fairness — all servers must return identical bodies/headers
pnpm bench:validate

# 2. Publishable comparison (5 runs, 4 concurrency levels, mean ± stddev + CV)
pnpm bench:compare --profile full

# Optional: pin server processes to CPU cores (Linux, taskset) for lower noise
node scripts/run.js --compare --profile full --pin 2-7

# Force a specific tool
node scripts/run.js --compare --tool autocannon
```

Results are written to `results/<timestamp>/` (JSON + a Markdown report) and copied to
`results/latest/`.

## How to use these numbers

1. Relative rankings on identical hardware are meaningful; absolute RPS is loopback-bound (the
   load generator shares the machine with the server) and hardware-specific.
2. In real apps, a single database call adds milliseconds per request — the gap between
   frameworks shrinks fast once real work is involved.
3. NextRush keeps a dependency-free core, ships adapters for several runtimes, and supports
   optional DI and decorators. Different trade-offs, not a single universal winner.

Run your own benchmarks on your own hardware. That is the only number that matters.
