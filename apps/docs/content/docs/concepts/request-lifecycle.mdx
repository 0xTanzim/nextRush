Understanding how requests flow through NextRush helps you write better middleware and debug issues faster.

## The Complete Flow

Every HTTP request passes through a small number of stages. The router is itself a middleware in the stack — not a separate layer — and it runs last, after every other middleware has had a chance to run.

    participant Client
    participant Adapter
    participant Middleware
    participant Handler

    Client->>Adapter: HTTP Request
    Adapter->>Adapter: Create Context

        Middleware->>Middleware: before next()

    end

    Middleware->>Handler: ctx with params
    Handler-->>Middleware: Response

    loop Middleware unwind (reverse)
        Middleware->>Middleware: after next()
    end

    Middleware-->>Adapter: done
    Adapter-->>Client: HTTP Response

## Stage by Stage

<Steps>
<Step>
### Adapter Creates Context

The adapter receives the raw HTTP request and creates a `Context` object. In the Node.js adapter, this happens inside `createHandler`:

```ts
// Simplified from @nextrush/adapter-node
const handler = app.callback();

return (req, res) => {
  const ctx = createNodeContext(req, res, { trustProxy });

  handler(ctx).then(
    () => {
      // Ensure response is sent if handler didn't respond
      if (!ctx.responded && !res.headersSent) {
        res.statusCode = ctx.status === 404 ? 404 : ctx.status;
        res.end();
      }
    },
    (error) => {
      // Last-resort error handling
      if (!res.headersSent) {
        res.statusCode = 500;
        res.end(JSON.stringify({ error: 'Internal Server Error' }));
      }
    }
  );
};
```

The `Context` object wraps the raw request and response. It parses the URL, method, headers, query string, and client IP at construction time.

Request properties are read-only and available immediately:

```ts
ctx.method; // 'GET', 'POST', etc.
ctx.url; // '/users/123?page=1'
ctx.path; // '/users/123'
ctx.query; // { page: '1' }
ctx.headers; // { 'content-type': 'application/json', ... }
ctx.ip; // Client IP (respects trustProxy option)
```

Mutable state is populated by middleware and the router during the request lifecycle:

```ts
ctx.status; // Initially 200
ctx.body; // Request body — undefined until body-parser middleware runs
ctx.params; // Route params — empty until router sets them
ctx.state; // {} — shared state bag for middleware
```

Response methods send data back to the client:

```ts
ctx.json(data); // Send JSON response
ctx.send(data); // Send text, buffer, or stream
ctx.html(str); // Send HTML
ctx.redirect(url); // Redirect (302 by default)
ctx.set(k, v); // Set response header
```

</Step>

<Step>
### Middleware Chain Executes

`app.callback()` builds a single request handler by composing the middleware stack with `compose()`. There is nothing else wrapping the chain — no per-plugin hook collection, no lifecycle events outside the middleware model itself. Any long-lived service that needs to touch every request (an [Extension](/docs/concepts/plugins)) does so by registering ordinary middleware inside its own `setup()`, before `app.ready()` freezes configuration.

Each middleware receives `(ctx, next)` and can run code before and after calling `next()`.

```ts
app.use(async (ctx) => {
  const start = Date.now(); // BEFORE
  await ctx.next(); // Continue to next middleware
  const ms = Date.now() - start; // AFTER (all downstream complete)
  ctx.set('X-Response-Time', `${ms}ms`);
});
```

Middleware executes like an onion — each layer wraps the next:

```
Request enters →
  ┌───────────────────────────────────────┐
  │  Middleware 1 (before)                │
  │  ┌───────────────────────────────┐    │
  │  │  Middleware 2 (before)        │    │
  │  │  ┌───────────────────────┐    │    │
  │  │  │  Router middleware    │    │    │
  │  │  │  ┌─────────────────┐  │    │    │
  │  │  │  │    Handler      │  │    │    │
  │  │  │  └─────────────────┘  │    │    │
  │  │  │  (router returns)     │    │    │
  │  │  └───────────────────────┘    │    │
  │  │  Middleware 2 (after)         │    │
  │  └───────────────────────────────┘    │
  │  Middleware 1 (after)                 │
  └───────────────────────────────────────┘
                            ← Response exits
```

<Callout type="warn">
  Calling `next()` more than once in a single middleware throws an error. The `compose()` function
  tracks dispatch index per request and rejects duplicate calls.
</Callout>

</Step>

<Step>
### Router Matches the Route

The app-owned router is mounted as the **last** middleware in the stack — `app.ready()` pushes it on after every extension has registered its own middleware, so the router always sees a fully-assembled `ctx` by the time it runs. When it executes, it matches the request path against registered routes using a two-tier strategy:

1. **Static routes** — O(1) hash map lookup (`"GET /users"` → handler)
2. **Dynamic routes** — O(k) segment trie traversal, where k is the number of path segments

```ts
const router = createRouter();

router.get('/users', listUsers); // Static: O(1) lookup
router.get('/users/:id', getUser); // Dynamic: trie traversal
router.get('/files/*', serveFile); // Wildcard: catches rest

app.route('/', router);
```

When a route matches, the router sets `ctx.params` and calls the pre-compiled handler executor. When no route matches, it sets `ctx.status = 404` and calls `next()` to let downstream middleware handle it.

```ts
// GET /users/123 matches router.get('/users/:id', getUser)
// ctx.params → { id: '123' }
```

When you mount a router with a prefix via `app.route('/api', router)`, the prefix is stripped from `ctx.path` before the router sees it, then restored after.

</Step>

<Step>
### Handler Runs

The matched handler runs with the populated context:

```ts
async function getUser(ctx) {
  const { id } = ctx.params;
  const user = await db.users.findById(id);

  if (!user) {
    ctx.status = 404;
    ctx.json({ error: 'User not found' });
    return;
  }

  ctx.json(user);
}
```

For class-based controllers (registered via `registerControllers()` from `nextrush/class`), the handler building pipeline adds steps before calling your method:

1. Execute guards (class-level, then method-level)
2. Resolve controller instance from the app's DI container
3. Extract parameters using decorators (`@Body`, `@Param`, etc.)
4. Call the controller method
5. Serialize the return value as JSON

</Step>

<Step>
### Response Finalization

After the handler completes and the middleware chain unwinds, the adapter ensures a response is sent. If your handler or middleware already called a response method (`ctx.json()`, `ctx.send()`, etc.), the context is marked as responded and no further action is taken.

If nothing responded, the adapter sends a fallback:

- **Status 404**: sends `{ "error": "Not Found" }`
- **Other status**: ends the response with the current `ctx.status`

</Step>
</Steps>

## Error Handling

Errors thrown at any stage are caught by `app.callback()`. There's a single error path: your custom handler (if set via `setErrorHandler`) runs, and if none is set — or it throws — the default handler responds.

```ts
// Set a custom error handler
app.setErrorHandler((error, ctx) => {
  if ('status' in error && typeof error.status === 'number') {
    ctx.status = error.status;
    ctx.json({ error: error.message });
  } else {
    ctx.status = 500;
    ctx.json({ error: 'Internal Server Error' });
  }
});
```

You can throw errors from anywhere in the middleware chain:

```ts
// HTTP error with status
ctx.throw(404, 'User not found');

// Error classes from nextrush
import { NotFoundError } from 'nextrush';
throw new NotFoundError('User not found');

// Plain errors become 500
throw new Error('Database connection failed');
```

<Callout type="warn">
  In production, the default error handler returns a generic "Internal Server Error" to avoid
  leaking internal details. Set a custom error handler to control error responses.
</Callout>

## Performance Characteristics

| Stage                | Complexity | Notes                            |
| -------------------- | ---------- | --------------------------------- |
| Context creation     | O(1)       | Object allocation + URL parsing  |
| Middleware execution | O(n)       | n = number of middleware          |
| Static route match   | O(1)       | Hash map lookup                   |
| Dynamic route match  | O(k)       | k = number of path segments       |
| JSON serialization   | O(s)       | s = response data size            |
