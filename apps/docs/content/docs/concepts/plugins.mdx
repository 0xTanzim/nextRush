NextRush has no `Plugin` interface. There is no `app.plugin()`. Capability is added through three idioms, and almost everything you write is the first one.

## The Three Kinds

<Callout type="info" title="Not equal in weight">
  These three kinds are not three equally-likely choices. Reach for **Middleware** by default.
  Reach for a **Registrar** when wiring class-based controllers. Reach for an **Extension** only
  when you're building long-lived, app-level infrastructure — which is rare.
</Callout>

| Kind | Idiom | Share of real usage | Examples |
| --- | --- | --- | --- |
| Middleware | `app.use(fn())` | ~99% | cors, helmet, body-parser, logger, static, rate-limit, compression, openapi, template |
| Registrar | direct import + call (`await` if async) | ~0.9% | `registerControllers(app, opts)`, `createWebSocket()` |
| Extension | `app.extend(ext)` + `await app.ready()` | ~0.1% | `events()` |

Most features you'll ever add — security headers, request logging, static files, API docs, HTML rendering — are middleware. You register them with `app.use()` and move on. A registrar wires up a subsystem (class-based controllers, a WebSocket server) with a plain function call. An Extension is reserved for framework-level, long-lived services that need a boot phase and a teardown phase — an event bus is the one example that ships today.

## Mental Model

Think of it as three different tools for three different jobs, not three tiers of the same tool:

- **Middleware** is a step in the request pipeline. It runs on every request, in registration order, and it's how almost all functionality — security, parsing, logging, rendering — gets attached to your app.
- **A Registrar** is setup code that runs once, before the server starts. It reads what it needs from the app (a router, a container) and configures it. It's a function, not an object with a lifecycle.
- **An Extension** is a long-lived service the app itself depends on for its whole lifetime — booted once at `app.ready()`, torn down once at `app.close()`. Writing one is a framework-author task, not something most application code needs.

## Middleware — the default (~99%)

Middleware is a function you pass to `app.use()`. Nearly every package NextRush ships — cors, helmet, body-parser, logger, static, rate-limit, compression, openapi, template — is middleware, because nearly everything an HTTP framework does is "run some logic for each request."

```typescript title="Adding capability via middleware"
import { createApp, listen } from 'nextrush';
import { cors } from '@nextrush/cors';
import { helmet } from '@nextrush/helmet';
import { openapi } from '@nextrush/openapi';

const app = createApp();

app.use(helmet());
app.use(cors());
app.use(openapi({ router: app.router!, info: { title: 'API', version: '1.0.0' } }));

await listen(app, 8080);
```

If you're writing your own reusable capability — a custom logger, a request-timing header, a feature flag check — write it as middleware first. Only reach for a Registrar or an Extension if middleware genuinely can't express what you need (see the next two sections for when that's true).

See [Middleware Internals](/docs/internals/middleware-internals) for how `app.use()` and `compose()` work under the hood.

## Registrar — plain functions for wiring (~0.9%)

A Registrar is not a type or an interface — it's a function you call directly, `await`ing it if it's async. It exists for subsystems that need to read from the app (its router, its DI container) and configure something at startup, rather than run per request.

The clearest example is `registerControllers()`, which scans for `@Controller`-decorated classes, resolves them through the app's DI container, and registers their routes on the app's router:

```typescript title="Registrar: wiring class-based controllers"
import 'reflect-metadata';
import { createApp, listen } from 'nextrush';
import { Controller, Get, Service, registerControllers } from 'nextrush/class';

@Service()
class UserService {
  findAll() {
    return [{ id: 1, name: 'Alice' }];
  }
}

@Controller('/users')
class UserController {
  constructor(private users: UserService) {}

  @Get() findAll() {
    return this.users.findAll();
  }
}

const app = createApp();
await registerControllers(app, { root: './src' }); // must be awaited before serve()
await listen(app, 8080);
```

`createWebSocket()` (from `@nextrush/websocket`) is the other current example — it's a factory you call directly, then attach with `app.use(wss.upgrade())`.

<Callout type="warn">
  A Registrar has no lifecycle hooks and no destroy step. It runs once, synchronously in effect
  (even if the function itself is `async`), and must complete before `listen()`/`serve()` starts
  the server — that's why `registerControllers()` is always awaited.
</Callout>

## Extension — rare, framework-level infrastructure (~0.1%)

An Extension is for a long-lived, app-scoped service that needs a real boot phase (possibly async, possibly depending on other extensions) and a real teardown phase on shutdown. It is registered with `app.extend()`, which only queues it — the actual `setup()` runs later, when `app.ready()` is called.

The event bus in `@nextrush/events` is the reference example:

```typescript title="Extension: a long-lived event bus"
import { createApp, listen } from 'nextrush';
import { events } from '@nextrush/events';

const app = createApp();

app.extend(events());
await app.ready(); // adapters call this automatically before start(), but you can call it yourself too

app.events.emit('server:started', {});
app.events.on('user:created', (data) => console.log(data));

await listen(app, 8080);
```

Before reaching for `app.extend()`, ask whether the capability could instead be middleware or a registrar — in the overwhelming majority of cases it can. Write an Extension only when you have state that must outlive any single request, must boot before the app starts serving traffic, and must clean up on shutdown.

### Writing an Extension

```typescript title="my-extension.ts"
import type { Extension } from '@nextrush/types';

export function myExtension(): Extension {
  return {
    name: 'my-extension',
    needs: [], // optional: names of other extensions that must register first
    setup(ctx) {
      // ctx: { app, logger, env, name, container?, decorate }
      ctx.decorate('myThing', someValue); // attach a value to app.myThing
      ctx.app.use(someMiddleware);
    },
    destroy() {
      // cleanup — runs in reverse registration order at app.close()
    },
  };
}
```

Declare the type it adds to `Application` via module augmentation:

```typescript
declare module '@nextrush/core' {
  interface Application {
    myThing: Foo;
  }
}
```

<Callout type="warn" title="There is no app.decorate()">
  Attaching a value to the app is only possible through `ctx.decorate()` inside `setup()` — this
  is intentional (RFC-NEXTRUSH-PLUGIN-SYSTEM §6.1). The only public, read-only way to check for a
  decoration from outside an extension is `app.hasDecorator(name)`.
</Callout>

## Extension Lifecycle

`app.extend()` is synchronous and only queues the extension — nothing runs yet. The actual boot work happens once, in registration order, when `app.ready()` is called:

<Mermaid
  chart="
flowchart TB
    A[app.extend(ext)] --> B[Queued — setup() NOT run yet]
    B --> C[app.ready() called]
    C --> D{needs satisfied?}
    D -->|No| X[Throw: needs unmet dependency]
    D -->|Yes| E[setup(ctx) runs, in registration order]
    E --> F[Configuration frozen — use/route/extend now throw]
    F --> G[Requests served]
    G --> H[app.close()]
    H --> I[destroy() runs, reverse order, Promise.allSettled]
    style A fill:#3b82f6,stroke:#1d4ed8,color:#fff
    style X fill:#ef4444,stroke:#dc2626,color:#fff
    style H fill:#ef4444,stroke:#dc2626,color:#fff
"
/>

Adapters (`listen()`, `serve()`) call `app.ready()` for you automatically before starting the server. You only need to call it yourself if you need extensions booted before some other setup step, or in tests that build a request handler without going through an adapter.

`app.ready()` is idempotent — calling it twice is safe. Once it resolves, the app's configuration is frozen: `use()`, `route()`, and `extend()` all throw if called afterward.

On shutdown, `app.close()` destroys extensions in **reverse registration order** using `Promise.allSettled`, so one failing `destroy()` never prevents the others from running. `close()` returns an `Error[]` — empty on success.

## Error Behavior

| Scenario | Error | When |
| --- | --- | --- |
| Duplicate extension name | `Error: Extension "X" is already registered` | `app.extend()` |
| `setup` is not a function | `TypeError: Extension must have a setup() method` | `app.extend()` |
| `extend()`/`use()`/`route()` after `ready()` | `Error: Cannot call X() after app.ready() — configuration is frozen` | any of those calls |
| `needs` dependency not yet registered | `Error: Extension "X" needs "Y", but "Y" was not registered before it` | `app.ready()` |
| Decoration name collision | `Error: Decoration "X" already exists on the application` | inside `setup()`, via `ctx.decorate()` |
| Extension `destroy()` throws | Error collected in the return array | `app.close()` |

Extension dependencies are declared, not auto-sorted: `needs` is asserted against registration order, not used to reorder anything. If your extension needs another extension's decoration, register that extension first and list it in `needs`.

## Performance Notes

- `app.extend()` is O(1) — it only pushes to an internal array and checks a `Set` for name collisions. No work happens until `ready()`.
- `setup()` for every registered extension runs once, at `ready()`, not per request. There is zero per-request extension overhead once the app is serving traffic — extensions only add per-request cost if their `setup()` itself registers middleware (which then behaves like any other middleware).
- `app.close()` runs every `destroy()` concurrently via `Promise.allSettled`, so shutdown time is bounded by the slowest `destroy()`, not their sum.

## Common Mistakes

### Reaching for an Extension when middleware would do

```typescript
// ❌ Overkill — a static value doesn't need a boot/teardown lifecycle
app.extend({
  name: 'config',
  setup(ctx) {
    ctx.decorate('config', loadConfig());
  },
});

// ✅ Just a constant, or middleware if it needs per-request access
const config = loadConfig();
app.use(async (ctx, next) => {
  ctx.state.config = config;
  await next();
});
```

### Forgetting to await a Registrar

```typescript
// ❌ registerControllers is async — routes may not exist yet when listen() runs
registerControllers(app, { root: './src' });
await listen(app, 8080);

// ✅ Await it first
await registerControllers(app, { root: './src' });
await listen(app, 8080);
```

### Registering an Extension after `ready()`

```typescript
await app.ready();
app.extend(events()); // ❌ throws — configuration is frozen after ready()
```

### Expecting `app.decorate()` to exist

```typescript
// ❌ There is no public app.decorate() — it only exists inside an Extension's setup()
app.decorate('myThing', value);

// ✅ Wrap it in an Extension
app.extend({
  name: 'my-thing',
  setup(ctx) {
    ctx.decorate('myThing', value);
  },
});
```
