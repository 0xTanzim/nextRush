The `Application` class is the central orchestrator of NextRush. It composes middleware, boots extensions, and handles errors — producing a request handler that adapters use to serve HTTP traffic.

## The Problem

Building a web server requires coordinating multiple concerns:

- Registering middleware in the correct order
- Booting long-lived services before the app starts serving traffic, and tearing them down cleanly on shutdown
- Handling errors consistently across all routes
- Producing a request handler that works across runtimes (Node.js, Bun, Deno)

Without a central orchestrator, you wire these together manually for every project — and get it wrong in different ways each time.

## How NextRush Solves This

The Application class provides a single entry point that:

1. **Composes middleware** — registers and chains middleware in insertion order
2. **Boots extensions** — a rare, opt-in mechanism for long-lived services with a setup/teardown lifecycle (see [Extending NextRush](/docs/concepts/plugins))
3. **Centralizes error handling** — a configurable error handler wraps the entire pipeline
4. **Produces a callback** — generates the request handler function that adapters need

## Mental Model

Think of Application as an **assembly line**:

- **Middleware** are the stations — each processes the request in order
- **Extensions** are rare, long-lived services booted once before the line starts running
- **Error handler** catches defects at any station
- **`callback()`** starts the line — adapters feed requests into it

The Application never processes requests directly. It builds the pipeline, then `callback()` snapshots it into a handler function.

## Execution Flow

When a request arrives, the handler produced by `callback()` runs the composed middleware chain (the onion model — see [Middleware Internals](/docs/concepts/middleware-internals)). If anything throws, the error handler runs instead.

```
Request → middleware₁ → middleware₂ → … → router → Response
```

Extensions do not participate per request — their `setup()` already ran once, at `app.ready()`, before the first request arrived. Anything an extension needs to run per request, it registers as ordinary middleware inside its own `setup()`.

## Minimal Usage

```typescript
import { createApp, createRouter, listen } from 'nextrush';

const app = createApp();

const router = createRouter();
router.get('/', (ctx) => ctx.json({ status: 'ok' }));

app.route('/', router);

await listen(app, 8080);
```

The `createApp()` factory from `nextrush` is **batteries-included** — it injects a default router automatically, so `app.get()`/`app.post()`/etc. work immediately. `@nextrush/core`'s own `createApp()` is a minimal engine with no router unless you pass one: `createApp({ router: createRouter() })`. Most application code should import `createApp` from `nextrush`.

## What Happens Automatically

When you call `app.callback()`, the Application:

- **Snapshots the middleware stack** — middleware added after `callback()` won't affect the returned handler
- **Wraps everything in error handling** — uncaught errors flow to the configured error handler

When adapters call `app.ready()` (automatically, before `start()`):

- Every registered extension's `setup()` runs once, in registration order, awaiting async setups
- The app-owned router is mounted last, so it runs after all middleware
- Configuration is frozen — `use()`, `route()`, and `extend()` all throw afterward

When you call `app.close()`:

- Sets `isRunning` to `false`
- Calls `destroy()` on each extension in reverse registration order using `Promise.allSettled`
- Clears decorations and the extension registry so the instance can be re-booted (useful in tests)
- Returns `Error[]` — any errors from extensions that failed to destroy

## Middleware Registration

```typescript
// Single middleware
app.use(async (ctx) => {
  console.log(`${ctx.method} ${ctx.path}`);
  await ctx.next();
});

// Multiple middleware at once
app.use(cors(), helmet(), json());

// Method chaining
app.use(cors()).use(helmet()).use(json());
```

Middleware executes in registration order (onion model). Each middleware runs its "before" logic, calls `next()`, then runs its "after" logic:

```
Request → cors → helmet → json → router → Response
              ↓      ↓      ↓      ↓
          (before) (before) (before) (handler)
              ↑      ↑      ↑      ↑
          (after)  (after) (after) (done)
```

Passing a non-function to `use()` throws a `TypeError`.

## Route Methods

```typescript
app.get('/users', handler);
app.post('/users', handler);
app.put('/users/:id', handler);
app.patch('/users/:id', handler);
app.delete('/users/:id', handler);
app.head('/users', handler);
app.all('/users', handler); // matches every HTTP method
```

Route methods delegate to the app-owned router (`app.router`). Calling them without a configured router throws — use `createApp()` from `nextrush`, or pass `{ router: createRouter() }` to `@nextrush/core`'s `createApp()`.

<Callout type="warn">
  There is intentionally no `app.options()` verb method — it would collide with the `app.options`
  configuration property. Register OPTIONS routes via `app.all()`, the router directly, or let CORS
  middleware handle preflight.
</Callout>

## Router Mounting

Mount routers at path prefixes using `app.route()`:

```typescript
import { createApp, createRouter } from 'nextrush';

const app = createApp();

const users = createRouter();
users.get('/', (ctx) => ctx.json([]));
users.get('/:id', (ctx) => ctx.json({ id: ctx.params.id }));

const posts = createRouter();
posts.get('/', (ctx) => ctx.json([]));

app.route('/users', users);
app.route('/posts', posts);
```

The `route()` method calls `router.routes()` internally — you don't need to call it yourself. Prefix boundaries are enforced, so `/users` won't match `/usersxyz`.

## Error Handling

### Setting an Error Handler

```typescript
app.setErrorHandler((error, ctx) => {
  console.error('Request failed:', error);

  if ('status' in error && typeof error.status === 'number') {
    ctx.status = error.status;
  } else {
    ctx.status = 500;
  }

  ctx.json({
    error: app.isProduction ? 'Internal Server Error' : error.message,
  });
});
```

Only one error handler is active at a time. Calling `setErrorHandler()` replaces any previous handler. The method returns `this` for chaining.

### Default Error Behavior

Without a custom handler, the Application uses its built-in error handler. It applies two independent rules:

| Concern          | Rule                                                              |
| ----------------- | ------------------------------------------------------------------ |
| Message exposure  | Shown only if `error.expose === true`. `HttpError` 4xx subclasses set `expose: true` by default; 5xx errors and plain `Error` objects never expose their message — in any environment. |
| Logging           | Runs when `!isProduction`, via `logger.error()`. Silent in production regardless of `expose`. |

A 404 with `expose: true` shows its real message in production. A 500 always returns `"Internal Server Error"` to the client, even in development — only the log output differs by environment.

If the error has a numeric `status` property in the 400–599 range, that status code is used. Otherwise, the response gets status 500.

<Callout type="warn">
  Logging depends on the configured `logger`. The default no-op logger produces no output. Pass
  `console` or a structured logger to see error logs.
</Callout>

If a custom error handler set via `setErrorHandler()` throws, NextRush logs the failure and falls back to this default handler.

### HTTP Error Classes

```typescript
import { NotFoundError, BadRequestError, UnauthorizedError } from 'nextrush';

app.use(async (ctx) => {
  throw new NotFoundError('User not found'); // 404
  throw new BadRequestError('Invalid email'); // 400
  throw new UnauthorizedError('Token expired'); // 401
});
```

## Extensions

Extensions are the rare (~0.1%) mechanism for long-lived, app-scoped services — see [Extending NextRush](/docs/concepts/plugins) for the full taxonomy of Middleware, Registrar, and Extension.

```typescript
import { events } from '@nextrush/events';

app.extend(events());
await app.ready(); // boots every registered extension; adapters call this for you

app.events.emit('server:started', {});
```

`app.extend()` is synchronous and only queues the extension — `setup()` doesn't run until `app.ready()`. Registering a duplicate extension name throws. Extensions cannot be registered after `app.ready()`.

## Lifecycle

Adapters call `app.ready()` (booting extensions and mounting the router) and then `app.start()` (marking the app as running) automatically before serving traffic. After `ready()`, `use()`, `route()`, and `extend()` throw to prevent unsafe mutations.

<Callout type="warn" title="Configuration Locks After ready()">
  Calling `app.ready()` freezes the application. Any attempt to register middleware, mount routers,
  or register extensions after this point throws an error.
</Callout>

```typescript
await app.ready();
app.start();
app.isRunning; // true
```

Call `app.close()` for graceful shutdown. It returns an array of errors from extensions that failed to destroy (empty on success).

```typescript title="Graceful Shutdown"
process.on('SIGTERM', async () => {
  const errors = await app.close();
  if (errors.length) console.error('Shutdown errors:', errors);
  process.exit(0);
});
```

## Performance Notes

- Middleware composition happens once at `callback()` time — no per-request overhead for building the chain
- Extension `setup()` runs once, at `ready()`, never per request
- Route mounting uses string prefix matching with boundary checks, not regex
- The middleware stack is a flat array with no tree traversal per request

## Security Considerations

- Enable `proxy: true` only behind a trusted reverse proxy. When disabled (default), `ctx.ip` uses the direct connection address.
- The default error handler hides error messages in production mode. Custom error handlers should avoid leaking stack traces or internal paths.
- Configuration is frozen after `ready()` — no middleware or extensions can be added while requests are in flight.

## Common Mistakes

### Forgetting to Mount a Router

```typescript
// ❌ Router defined but never mounted
const router = createRouter();
router.get('/users', handler);

// ✅ Mount it
app.route('/api', router);
```

### Wrong Middleware Order

```typescript
// ❌ Auth middleware after routes — routes run unprotected
app.route('/api', router);
app.use(authMiddleware);

// ✅ Security middleware before routes
app.use(authMiddleware);
app.route('/api', router);
```

### Not Awaiting a Registrar

```typescript
// ❌ registerControllers is async — routes may not exist yet
registerControllers(app, { root: './src' });
await listen(app, 8080);

// ✅ Await it before starting the server
await registerControllers(app, { root: './src' });
await listen(app, 8080);
```

### Not Awaiting Close

```typescript
// ❌ Extensions may not clean up
app.close();
process.exit(0);

// ✅ Wait for cleanup
await app.close();
process.exit(0);
```

## When Not To Use

The Application class is the right choice for most NextRush apps. Consider alternatives when:

- You need a standalone router without middleware or extensions — use `createRouter()` directly
- You're building a lightweight function handler for serverless — the adapter alone may suffice
