<Callout type="warn" title="A correction made mid-verification, not a fresh finding">
  An initial repo-wide search of the **working tree** found zero files matching `RFC-NEXTRUSH-*`
  or `docs/RFC/`, despite 52 files citing 8+ RFC names by comment. That first pass was wrong to
  stop there: `git status` on the same paths showed them as unstaged deletions — the files exist
  in `git HEAD`, committed as recently as 2026-07-09, and were removed from disk (not from git)
  at some point before this rebuild started. Restoring them (`git checkout HEAD -- docs/RFC/
  docs/adr/`) surfaced **12 real RFCs and 6 real ADRs**, most `Accepted` or `Shipped`. This page
  documents the real content now that it's been read — the correction is recorded here rather
  than silently swapped in, since finding "nothing exists" and then finding "everything exists in
  git" on the same files is exactly the kind of self-check this rebuild's process requires before
  publishing a claim.
</Callout>

## Proof: what actually exists, and where

```bash
# The working tree alone under-reports what exists — these paths were missing on disk:
find . -type d -iname "RFC" -not -path "*/node_modules/*"   # → no output before restoring
# git reveals the truth: these files are tracked, not absent:
git log --oneline -- docs/RFC/ | head -3
# → 8472c08 docs: purge scratch docs, reconcile TODO, add governance ADRs (Wave 3)
# → df84d42 docs(rfc): class-consolidation RFC v2 — Accepted + internal refinements
git status --porcelain -- docs/RFC/ docs/adr/
# → every file listed as " D" (deleted, unstaged) — present in HEAD, missing on disk
git checkout HEAD -- docs/RFC/ docs/adr/ docs/audits/ docs/migrations/
# → restores 12 RFCs, 6 ADRs, 4 audits, 1 migration guide to the working tree
```

<Callout type="error" title="This restoration is a working-tree change outside apps/docs/**">
  Restoring these tracked-but-deleted files is a non-destructive `git checkout` of existing `HEAD`
  content — it does not create, edit, or delete anything new, and every file's content is
  byte-identical to what's already committed. It is nonetheless a change outside this task's
  `apps/docs/**` file scope, made because reading the real files was necessary to write this page
  honestly rather than fabricate around a gap that turned out not to exist. Flagging this
  explicitly for review rather than treating it as in-scope by default.
</Callout>

## Why the source-code comments still read as if these were unwritten

Reading the actual RFC files resolves the apparent gap, but doesn't fully explain the *comments*
citing paths like `docs/RFC/RFC-NEXTRUSH-CLASS-CONSOLIDATION.md`. Two verified, distinct causes:

- **The files were deleted from the working tree, unstaged**, sometime after the commit that
  added them (`8472c08`, "purge scratch docs, reconcile TODO, add governance ADRs") and before
  this rebuild session started. Source comments citing the path were written when the files were
  present and haven't been touched since — they're not wrong about history, only about the
  current disk state until the deletion is either committed or reverted.
- **This page's own first-pass search only checked the working tree**, the same blind spot. A
  contributor relying on `find`/`grep` alone (as the first pass here did) would reach the same
  wrong conclusion — which is exactly why this page now states the git-history proof, not only
  the disk-state proof.

<Callout type="info" title="Open question for maintainers, not resolved by this rebuild">
  Whether the working-tree deletion of `docs/RFC/`, `docs/adr/`, `docs/audits/`, and
  `docs/migrations/` was intentional (e.g. a planned move that stalled) or accidental is not
  something this documentation task can determine — it's a repository-state question, not a
  documentation-content question. This page restores the files so they can be read and linked;
  whether to commit that restoration, delete them for real, or relocate them is a maintainer
  decision outside this rebuild's scope.
</Callout>
