<DocHero eyebrow="Runtime · Event-driven">

Serverless platforms invoke your handler per event and can terminate the execution environment
between calls — there's no process to keep alive, only a warm instance you might get to reuse.
Same `createApp`/`createRouter` API as Node, deployed behind a one-line handler. The tradeoff is
cold starts on a fresh instance and a deployment model built around short-lived invocations, not
a server you manage.

## Prerequisites

- **Required:** a terminal, a package manager, and an AWS account if you plan to deploy. No
  prior NextRush knowledge assumed.
- **Difficulty · time:** Beginner · ~10 minutes

<Steps>

### Step 1 of 4 — Install NextRush and the serverless adapter

**Why now:** like the other non-Node runtimes, the `nextrush` meta-package does not bundle a
runtime adapter — it ships only `@nextrush/adapter-node`. Running on Lambda means adding
`@nextrush/adapter-serverless` alongside it.

**Do:**

<PackageInstall packages={['nextrush', '@nextrush/adapter-serverless']} />

**Why it worked:** `createApp` and `createRouter` still come from `nextrush` — those two are
runtime-independent. The Tier-1 handler factory (`createLambdaHandler`) comes from
`@nextrush/adapter-serverless` instead, for the same reason as Bun, Deno, and edge: the
meta-package's `listen` re-export targets `@nextrush/adapter-node` specifically, and there is no
`listen()` on a platform that invokes your code per event rather than running a process.
`createLambdaHandler` covers AWS Lambda Function URLs and both API Gateway payload formats (HTTP
API v2, REST API v1) — it detects which event shape it received, so you never name a provider or
touch a mapper (see [Event mapping](/docs/concepts/event-mapping) for how that detection and
translation actually works). Google Cloud Functions and Azure Functions have their own Tier-1
handlers (`createGoogleHandler`, `createAzureHandler`) exported from the same package.

### Step 2 of 4 — Write a hello-world Lambda handler

**Do:** create `index.ts`:

```ts title="index.ts"
import { createApp, createRouter } from 'nextrush';
import { createLambdaHandler } from '@nextrush/adapter-serverless';

const app = createApp();
const router = createRouter();

router.get('/', (ctx) => {
  ctx.json({ runtime: ctx.runtime, status: 'ok' });
});

app.route('/', router);
export const handler = createLambdaHandler(app);
```

Deploy it behind a Lambda Function URL (or API Gateway) using your usual AWS tooling — the
handler shape (`(event, context?) => Promise<result>`) is the plain AWS Lambda contract, so no
NextRush-specific deploy step is required.

**Expected output:**

```bash
curl https://your-function-url.lambda-url.us-east-1.on.aws/
# → {"runtime":"edge","status":"ok"}
```

**Why it worked:** `createLambdaHandler(app)` wires the AWS event mappers for you and reuses the
edge adapter's fetch engine underneath — the same per-invocation execution model
(stateless, timeout→504, warm-instance reuse) the edge adapter uses for Cloudflare Workers,
translated from a Lambda event to a Web `Request` and back. `ctx.runtime` reports `'edge'`
because `createLambdaHandler` is built directly on `@nextrush/adapter-edge`'s fetch engine, and
`EdgeContext` sets `runtime` from `detectEdgeRuntime()` — which has no AWS-aware branch and
falls through to the generic `'edge'` default on Lambda (it only special-cases Cloudflare,
Vercel, and Netlify). `ctx.runtime` here identifies the *adapter family* your handler is built
on, not the platform invoking it — don't rely on it to distinguish Lambda from Cloudflare
Workers.

### Step 3 of 4 — Build the handler once, at module scope

**Why now:** the pattern above works, but where you call `createApp()` and `createLambdaHandler()`
determines whether Lambda's warm-instance reuse actually helps you.

**Do:** keep app construction and handler creation at module scope, never inside the handler
function:

```ts title="index.ts"
import { createApp, createRouter } from 'nextrush';
import { createLambdaHandler } from '@nextrush/adapter-serverless';

// Module scope — runs once per cold start, reused across every warm invocation.
const app = createApp();
const router = createRouter();
router.get('/', (ctx) => ctx.json({ status: 'ok' }));
app.route('/', router);

export const handler = createLambdaHandler(app);
```

**Why it matters:** serverless platforms keep a "warm" instance alive between invocations, and
`createLambdaHandler` memoizes the boot barrier — `app.ready()` runs exactly once, even under
concurrent warm invocations, and the booted handler is reused across every subsequent call on
that instance. Calling `createApp()` or `createLambdaHandler()` inside the handler function
re-boots the application on every invocation and defeats warm reuse entirely — the cost you pay
once at cold start would repeat on every request instead.

<Callout type="warn">
Don't put mutable request state in module-scope variables. Each invocation builds a fresh
`Context`, so `ctx.state`, headers, and body never leak between invocations on the same warm
instance — but a module-scope `let` you write to yourself will leak, because that variable
survives across invocations exactly like the app instance does.
</Callout>

### Step 4 of 4 — Know what changes with per-invocation execution

**What's genuinely different, and why:** there is no long-running process — the platform invokes
your handler per event and may terminate the execution environment between invocations, so the
first invocation on a fresh instance pays a cold-start cost (running `app.ready()` for the first
time) that later warm invocations on the same instance skip. `createLambdaHandler` buffers the
full response body into the result before returning it, because that's the shape a plain Lambda
result requires; if you need true response streaming — lower time-to-first-byte, an unbounded
body — use the dedicated `createLambdaStreamingHandler` instead, which writes chunks to Lambda's
`responseStream` as your app produces them via `ctx.sendStream(...)`, instead of collecting the
whole body first. The regular `createLambdaHandler`'s `timeout` option is also intentionally
narrow: it accepts a per-invocation millisecond cap and nothing else — a `streaming` tuning flag
is deliberately not exposed yet, because true Function URL streaming support is still landing,
and the adapter's own source notes a no-op flag there would be misleading rather than adding one
prematurely.

**What's identical:** the Context API (`ctx.json`, `ctx.params`, `ctx.query`, `ctx.set`, …),
`createApp`, `createRouter`, route registration, and middleware all behave the same as Node —
nothing in your route handler above is Lambda-specific, and the same app code moves to Google
Cloud Functions or Azure Functions by swapping `createLambdaHandler` for `createGoogleHandler` or
`createAzureHandler`.

`@nextrush/adapter-serverless` is versioned independently at `1.0.0`, following the same
mixed-version policy as every other post-v3 package — see [Versioning](/docs/architecture) for
why. It doesn't yet have its own row in the [compatibility
matrix](/docs/help/compatibility-matrix)'s runtime support table, which currently only
tracks Node, Bun, Deno, and the edge targets. Check the [serverless adapter
reference](/docs/reference/platforms/serverless) for the complete surface, including the Tier-3
`EventMapper` API for platforms NextRush doesn't ship a handler for, before pinning a
production version.

</Steps>

## Checkpoint

Confirm the function answers before moving on — if your output matches this, you're ready for
what's next:

```bash
curl -i https://your-function-url.lambda-url.us-east-1.on.aws/
# → HTTP/1.1 200 OK
# → {"runtime":"edge","status":"ok"}
```

Your project now looks like:

```text
my-function/
  package.json
  index.ts
```

**🎉 That's a real Lambda invocation, warm reuse and all.** The handler you built at module
scope is exactly what makes the next invocation on the same warm instance skip the boot cost this
one paid.

## What you learned

Four things now describe how a request reaches your code on Lambda:

- **`nextrush` gives you the runtime-independent half** — `createApp`, `createRouter`, and route
  registration are identical on Lambda and Node. [Runtime compatibility
  concept](/docs/concepts/runtime-compatibility)
- **`createLambdaHandler` comes from `@nextrush/adapter-serverless`, not the meta-package** —
  along with `createGoogleHandler` and `createAzureHandler` for the other two providers.
- **Module-scope construction is what makes warm reuse work** — building the app inside the
  handler function re-boots it on every invocation.
- **Response buffering is the default; true streaming is a separate handler** —
  `createLambdaStreamingHandler` when time-to-first-byte or body size matters.
