```bash
# create a task
curl -X POST http://localhost:8080/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"Write the docs"}'
# → {"id":1,"title":"Write the docs","done":false}

# read that exact task back
curl http://localhost:8080/tasks/1
# → {"id":1,"title":"Write the docs","done":false}

# ask for one that was never stored
curl -i http://localhost:8080/tasks/999
# → HTTP/1.1 404 Not Found
```

That `999` returning a real 404 — not a hardcoded record — is the point of the build. The `GET`
hands back what the `POST` stored, and the miss case is honest.

This is the hand-wired path: you assemble the server yourself so the router, the store, and middleware
order stay visible. Want a project generated for you instead?
Use [create-nextrush](/docs/start/create-nextrush).

## The request pipeline you're about to build

Nothing here is Task-API-specific — this is the shape of every request in every NextRush app.

## Why a Task API, specifically

A weather-lookup demo teaches one route and stops. A Task API forces four real backend concerns at once:

```text
Storage     — remember state between requests
Input       — parse and validate a POST body before you trust it
Lookup      — resolve a route param to a real record, or fail honestly
Errors      — "not found" and "bad request" as real HTTP responses
```

Build those four once and you've built them for Users, Orders, or anything else with the same shape.

### Step 1 / 5 — Create the project

**Why now:** a NextRush app is an ordinary Node project first. The folder and `package.json` come
before any framework code — NextRush is a library you import, not a project layout you adopt.

```bash
mkdir task-api && cd task-api
pnpm init
```

Add `"type": "module"` to `package.json`. NextRush is ESM-only — without that line, `import`
fails later as a confusing `SyntaxError` far from its real cause.

**Check:** open `package.json` and confirm `"type": "module"` is there before continuing.

### Step 2 / 5 — Install NextRush

**Why now:** the framework must be on disk before Step 3 can import it. You also install
`@nextrush/body-parser` here even though you use it in Part 2 — so the install step stays in one place.

<PackageInstall packages={["nextrush", "@nextrush/body-parser"]} dev={["tsx", "typescript", "@types/node"]} />

What you get:

- ✓ `nextrush` — framework meta-package (`createApp`, `createRouter`, `listen`)
- ✓ `@nextrush/body-parser` — JSON parsing, wired in Part 2
- ✓ `tsx` — run TypeScript directly while you iterate

**Why it worked:** body parsing is a separate package on purpose — the core stays zero-dependency;
you only pay for JSON parsing on routes that need it.

### Step 3 / 5 — Start a server with one route

**Why now:** prove the shortest path works end to end before storage or input — Adapter → Router →
Handler, nothing else attached.

Create `src/index.ts`:

```ts title="src/index.ts"
import { createApp, createRouter, listen } from 'nextrush';

const app = createApp();
const router = createRouter();

router.get('/', (ctx) => {
  ctx.json({ name: 'Task API', status: 'ok' });
});

app.route('/', router);
await listen(app, 8080);
```

```bash
npx tsx src/index.ts
```

```bash
curl http://localhost:8080/
# → {"name":"Task API","status":"ok"}
```

Silence in the server terminal is expected — the default logger is a no-op.

**Why it works**

- `createApp()` owns the middleware pipeline
- `createRouter()` holds routes; `app.route('/', router)` mounts it
- `listen(app, 8080)` starts serving
- handlers talk through [Context](/docs/concepts/context) — `ctx.json(...)` writes the response

<Steps>

### Step 4 / 5 — Accept data with `POST`

**Why now:** a fixed message isn't storing anything. This step adds a store and a create route —
which means reading a body, which is where middleware earns its place.

**What this step adds**

- ✓ In-memory `Map` as the store
- ✓ `app.use(json())` **before** the routes
- ✓ `POST /tasks` + `GET /tasks`

```diff
  const app = createApp();
+ app.use(json());

  const router = createRouter();
+ router.post('/tasks', (ctx) => { ... });
```

<details>
<summary>Full <code>src/index.ts</code> after this step</summary>

```ts title="src/index.ts"
import { createApp, createRouter, listen, BadRequestError } from 'nextrush';
import { json } from '@nextrush/body-parser';

type Task = { id: number; title: string; done: boolean };

const tasks = new Map<number, Task>();
let nextId = 1;

const app = createApp();

// Parse JSON bodies before any route runs — without this, ctx.body stays undefined.
app.use(json());

const router = createRouter();

router.get('/tasks', (ctx) => {
  ctx.json([...tasks.values()]);
});

router.post('/tasks', (ctx) => {
  const body = ctx.body as { title?: string };
  if (!body?.title) throw new BadRequestError('title is required');

  const task: Task = { id: nextId++, title: body.title, done: false };
  tasks.set(task.id, task);

  ctx.status = 201;
  ctx.json(task);
});

app.route('/', router);
await listen(app, 8080);
```

</details>

Restart (`Ctrl+C`, then `npx tsx src/index.ts`), then create a task:

```bash
curl -X POST http://localhost:8080/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"Write the docs"}'
# → {"id":1,"title":"Write the docs","done":false}
```

**Why it works**

- Request order: Adapter → `json()` fills `ctx.body` → Router → Handler
- Pipeline runs top to bottom — `app.use(json())` must sit **above** `app.route(...)`
- `createApp()` owns middleware; `createRouter()` only matches paths

<WhatChanged
  before="Adapter → Router → Handler"
  after="Adapter → json() → Router → Handler"
  note="Register the parser after the routes and ctx.body is still undefined when the handler runs."
/>

<Callout type="warn">
If a `POST` handler sees `ctx.body` as `undefined`, the parser ran too late or wasn't registered.
`app.use(json())` has to sit above the router — not inside a handler, not after `app.route(...)`.
</Callout>

**Try this:** send `curl -X POST http://localhost:8080/tasks -H 'Content-Type: application/json'
-d '{}'` — no `title`. You should get a `400`, not a crash and not a silently created task.

</Steps>

<Steps>

### Step 5 / 5 — Read it back, or return a real 404

**Why now:** storing only matters if you can fetch. A misleading empty `200` leaves callers guessing
whether "empty" means "missing" or "not found yet."

**What this step adds**

- ✓ `GET /tasks/:id` — route param resolved against the store
- ✓ `NotFoundError` — thrown, not returned, when the lookup misses

```diff
  router.get('/tasks', (ctx) => {
    ctx.json([...tasks.values()]);
  });

+ router.get('/tasks/:id', (ctx) => {
+   const task = tasks.get(Number(ctx.params.id));
+   if (!task) throw new NotFoundError('Task not found');
+   ctx.json(task);
+ });
```

<details>
<summary>Full <code>src/index.ts</code> — the finished Task API</summary>

```ts title="src/index.ts"
import { createApp, createRouter, listen, BadRequestError, NotFoundError } from 'nextrush';
import { json } from '@nextrush/body-parser';

type Task = { id: number; title: string; done: boolean };

const tasks = new Map<number, Task>();
let nextId = 1;

const app = createApp();
app.use(json());

const router = createRouter();

router.get('/tasks', (ctx) => {
  ctx.json([...tasks.values()]);
});

router.post('/tasks', (ctx) => {
  const body = ctx.body as { title?: string };
  if (!body?.title) throw new BadRequestError('title is required');

  const task: Task = { id: nextId++, title: body.title, done: false };
  tasks.set(task.id, task);

  ctx.status = 201;
  ctx.json(task);
});

router.get('/tasks/:id', (ctx) => {
  const task = tasks.get(Number(ctx.params.id));
  if (!task) throw new NotFoundError('Task not found');
  ctx.json(task);
});

app.route('/', router);
await listen(app, 8080);
```

</details>

```bash
curl -X POST http://localhost:8080/tasks \
  -H 'Content-Type: application/json' -d '{"title":"Write the docs"}'
# → {"id":1,"title":"Write the docs","done":false}

curl http://localhost:8080/tasks/1
# → {"id":1,"title":"Write the docs","done":false}

**Why it works**

- `:id` → `ctx.params.id` (string) → `Number(...)` for the store key
- throw `NotFoundError` → built-in handler maps it to status + JSON
- same Router / Handler shape as Parts 1–2 — one more route and a real failure path

## What you built

Concrete deliverables:

- ✓ **Application** — `createApp()`, owning the middleware pipeline
- ✓ **Router** — `createRouter()`, mounted with `app.route()`
- ✓ **Store** — in-memory `Map` across requests

- ✓ **Two error paths** — real `400` for bad input, real `404` for a missing id

## What you learned

Mental models (not the file list):

- **Request pipeline** — Adapter → Middleware → Router → Handler → Context, both directions
- **Routing** — `createRouter()`, `/tasks/:id`, mount with `app.route()` — [Routing deep dive](/docs/concepts/routing)
- **Context** — `ctx.body`, `ctx.params`, `ctx.json()`, `ctx.status` — [Context deep dive](/docs/concepts/context)
- **Middleware order** — `json()` before the router or `ctx.body` is empty — [Middleware deep dive](/docs/concepts/middleware)
- **Errors** — throw `HttpError`, framework maps status — [Error handling](/docs/guides/error-handling)

A bigger app is this same pipeline with more middleware and more routes — not a different shape.

## Think like an architect

These turn copying into understanding:

- Why create a router and mount it with `app.route('/', router)`, rather than adding a route
  straight to `app`?
- Why does `app.use(json())` have to sit above the router instead of inside a handler?
- Why is a thrown `NotFoundError` better for a missing id than `ctx.json(null)` with a `200`?

// DELETE /tasks/:id — remove a task, or 404 if it was never there.
router.delete('/tasks/:id', (ctx) => {
  const existed = tasks.delete(Number(ctx.params.id));
  if (!existed) throw new NotFoundError('Task not found');

  ctx.status = 204; // No Content — nothing to send back

});
```
