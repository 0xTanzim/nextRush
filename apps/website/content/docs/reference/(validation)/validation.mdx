## Why This Package Exists

Validating request input is something every API does, yet hand-rolled validation is where bugs and inconsistency creep in: every handler reinvents type and presence checks, error shapes drift between routes, and `ctx.body` stays `unknown` without a validation step forcing a cast.

NextRush ships the glue, not a validator. You bring the schema library you already use; `@nextrush/validation` runs it and produces one consistent, secure error shape.

## Minimal Usage

```ts
import { createApp } from '@nextrush/core';
import { json } from '@nextrush/body-parser';
import { validate } from '@nextrush/validation';
import { z } from 'zod';

const app = createApp();
const User = z.object({ name: z.string().min(1), email: z.string().email() });

app.post('/users', json(), validate(User), (ctx) => {
  const body = ctx.body; // validated and coerced
  ctx.status = 201;
  ctx.json(body);
});
```

On success, `ctx.body` **is** the validated, coerced value — no separate accessor.

## `validate(schema)` / `validate(spec, options)`

**Signature:**

```ts
function validate(
  arg: StandardSchemaV1 | RequestSchemas,
  options?: ValidateOptions
): Middleware;

function createValidate(defaultOptions?: ValidateOptions): typeof validate;
```

<TypeTable
  title="ValidateOptions"
  types={{
    errorStatus: {
      type: 'number',
      description: 'HTTP status to emit on validation failure (integer between 400 and 499).',
      default: '400',
      optional: true,
    },
  }}
/>

| Form | Validates |
| --- | --- |
| `validate(schema, options?)` | the request body against `schema` |
| `validate({ body?, query?, params? }, options?)` | each provided target against its own schema |

**Behavior:**

- On success: overwrites `ctx.body` with the coerced value; stores all coerced targets on `ctx.state.validated` (read via `validated(ctx)`); leaves `ctx.query`/`ctx.params` unmodified; calls `next()`.
- On failure: throws `ValidationError` with `status: options.errorStatus ?? 400`, aggregating every issue across every validated target — never calls `next()`.
- Atomic across targets: if any target fails, `ctx.body` is not overwritten.
- A schema whose own validator throws an unexpected error (not a validation failure) propagates unchanged — it is never swallowed into the failure status.

### Validating Multiple Targets and Reading Coerced Input

```ts
import { validate, validated } from '@nextrush/validation';
import { z } from 'zod';

const ParamsSchema = z.object({ id: z.string().uuid() });
const QuerySchema = z.object({
  page: z.coerce.number().int().min(1).default(1),
  sort: z.enum(['asc', 'desc']).default('asc'),
});

app.get(
  '/users/:id',
  validate(
    {
      params: ParamsSchema,
      query: QuerySchema,
    },
    { errorStatus: 422 }
  ),
  (ctx) => {
    // Access typed coerced values via validated(ctx):
    const { params, query } = validated<{
      params: { id: string };
      query: { page: number; sort: 'asc' | 'desc' };
    }>(ctx);

    // Or use target-specific helpers:
    const page = validated.query<{ page: number; sort: string }>(ctx)?.page;
    const id = validated.params<{ id: string }>(ctx)?.id;

    ctx.json({ id, page, sort: query.sort });
  }
);
```

## Reading Coerced Values: `validated(ctx)`

`ctx.query` and `ctx.params` are declared as string maps. In order to keep TypeScript honest without dangerous type casts, `@nextrush/validation` exposes all coerced values via the `validated` helper.

```ts
import { validated } from '@nextrush/validation';

// Read all coerced targets:
const { body, query, params } = validated(ctx);

// Generic type parameter:
const { query } = validated<{ query: { limit: number } }>(ctx);

// Target-specific helpers:
const query = validated.query<{ limit: number }>(ctx);
const params = validated.params<{ id: string }>(ctx);
const body = validated.body<MyUserType>(ctx);
```

When validation has not run, `validated(ctx)` safely returns `{}` so destructuring never throws, and target helpers return `undefined`.

## Project-Wide Validation: `createValidate(defaultOptions)`

If your API mandates `422 Unprocessable Entity` for all schema failures, avoid repeating `{ errorStatus: 422 }` on every route with `createValidate`:

```ts title="src/lib/validation.ts"
import { createValidate } from '@nextrush/validation';

export const validate = createValidate({ errorStatus: 422 });
```

```ts title="src/routes/items.ts"
import { validate, validated } from '../lib/validation';

// Reusable validator with 422 status baked in:
app.get('/items', validate({ query: QuerySchema }), (ctx) => {
  const { query } = validated(ctx);
  ctx.json(query);
});

// Route-level options still override the default when needed:
app.post('/auth/login', validate(LoginSchema, { errorStatus: 400 }), handler);
```

## One Source of Truth

<TypeTable
  title="Behavior by target"
  types={{
    body: { type: 'unknown', description: 'Validated, coerced, and written back to ctx.body as well as ctx.state.validated.body.' },
    query: { type: 'Record<string, string | string[]>', description: 'Validated; left as original string maps on ctx.query. Coerced values available via validated.query(ctx).' },
    params: { type: 'Record<string, string>', description: 'Validated; left as original string maps on ctx.params. Coerced values available via validated.params(ctx).' },
  }}
/>

**Why body overwrites and query/params don't:** `ctx.body` is typed `unknown`, so replacing it with the coerced object is honest — the static type never disagrees with the runtime value. `ctx.query`/`ctx.params` are declared as `string` maps; writing a coerced `number` back would make TypeScript claim `string` while the runtime holds a `number`. Coerced query and params values are stored on `ctx.state.validated` and read cleanly with `validated(ctx)` or `validated.query/params(ctx)`.

## Middleware Order

`validate()` validates the **already-parsed** `ctx.body` — it does not read the request stream. Place it after the body parser:

```ts
app.post(
  '/users',
  json(), // 1. parses the body → ctx.body
  validate(User), // 2. validates ctx.body, replaces it with the coerced value
  handler // 3. reads the validated ctx.body
);
```

If no body parser ran, `ctx.body` is `undefined`, and the schema decides the outcome (a required object schema rejects it with a 400).

## Errors & Status Codes

Failures throw the framework's existing `ValidationError` from `@nextrush/errors` — there is no separate error type for this package. It is rendered automatically by the framework's error handler, and `toJSON()` strips raw input so passwords or tokens never leak into the response:

```json
{
  "error": "ValidationError",
  "message": "Validation failed",
  "code": "VALIDATION_ERROR",
  "status": 422,
  "issues": [
    { "path": "body.email", "message": "Invalid email address" },
    { "path": "query.sort", "message": "Invalid enum value. Expected 'asc' | 'desc'" }
  ]
}
```

The error status defaults to `400 Bad Request`, but can be set per route via `errorStatus`, project-wide via `createValidate({ errorStatus })`, or globally in `@nextrush/errors` via `errorHandler({ validationErrorStatus: 422 })`.

`ValidationError` and `ValidationIssue` are re-exported from `@nextrush/validation` for a single import site:

```ts
import { ValidationError } from '@nextrush/validation';

app.use(async (ctx, next) => {
  try {
    await next();
  } catch (err) {
    if (err instanceof ValidationError) {
      ctx.status = err.status;
      ctx.json(err.toJSON());
      return;
    }
    throw err;
  }
});
```

## Security

- Standard Schema issues never carry the offending value, and `ValidationError.toJSON()` strips `received` — invalid passwords or tokens never appear in an error response.
- No prototype pollution: issue paths are joined only into display strings (`body.__proto__.x` is a label, never an assignment).
- Fail-closed: a schema that signals failure with an empty issues array still rejects the request — validation never silently passes.
- `errorStatus` is bounded to `400..499` at construction time — rejecting server error codes (5xx) or redirect codes (3xx) before any request runs.

## Runtime Compatibility

Zero runtime dependencies beyond `@nextrush/types` and `@nextrush/errors`. Runs anywhere NextRush runs: Node.js 22+, Bun 1.0+, Deno 1.0+, Cloudflare Workers, Vercel Edge.

## Non-Goals

- **Mutating `ctx.query`/`ctx.params` in-place** — left as string maps for type honesty; coerced values are cleanly accessed via `validated(ctx)`.
- **A schema DSL** — your schema library is the DSL.
- **Body parsing** — that is [`@nextrush/body-parser`](/docs/reference/body-parser)'s job.
- **Response validation** — planned alongside `@nextrush/openapi`.
